App Lab UI Studio

Three weeks, six 90-minute classes, eighteen 30-minute mini-app cycles. Students build confidence with visible controls and immediate feedback while teacher templates carry the math, variables, conditionals, random numbers and drawing logic.

18-cycle sequenceElement mapAssessment54 app sketchesVocabulary

How to run this studio

The design goal is a working app in each half hour. Every cycle follows the same rhythm: 3 minutes to meet a purpose, 5 minutes to see one idea, 5 minutes to try a small step together, 14 minutes to build, and 3 minutes to test and explain. The repeated rhythm lowers the amount of new information students must hold in mind.

Student job

Drag and name Design Mode elements. In Blocks mode, place or change only UI Controls blocks: onEvent, setText, getText, getNumber, getChecked, getProperty, setProperty, showElement, hideElement, setScreen, playSound, stopSound.

Teacher job

Prebuild all logic from other categories. Paste the annotated teacher code into App Lab text mode, switch to Blocks, verify it runs, then make a student remix. For a challenge, remove one or two UI blocks in Blocks mode after the working version is saved. Give students the sketch and the ID list.

Confidence rule

One fresh element or behavior per cycle. Start with a working model, make success visible within five minutes, test the smallest possible change, and let students choose topic or wording only after the core works. Treat the first bug as useful evidence.

Before class: run each teacher reference in your App Lab account and confirm that text-to-Blocks conversion works. The local files have been checked for structure and JavaScript syntax, but App Lab assets, permissions, Chart, Photo Select, and Canvas behavior depend on the live environment. If a chart reference cannot round-trip to Blocks, build the Data block once in Blocks mode and remix that project.

One ID rule for every app

Every Design Mode element ID uses camelCase and begins with its element type: buttonCalculate, textInputName, labelResult, radioButtonWalk, photoSelectPhoto, screenHome. The first word groups elements of the same type when IDs are sorted A to Z. Screen IDs follow the same rule. The annotated sketch and student card give the exact ID for each element.

Students should recognize every element, explain its input/output role, set a meaningful ID, and use its main Design Mode properties. Routines that keep the room moving

Three chunks on every student card

  1. Build the screen: drag only the named elements and set IDs.
  2. Connect behavior: add or change only the named UI blocks.
  3. Prove it: run two contrasting tests and explain the input and output.

Debugging ladder

  1. Did the app run?
  2. Is the element present on the current screen?
  3. Does the ID match exactly, including capitals?
  4. Is the event click, change, or input as intended?
  5. Does the output block point to the correct label, image or screen?

Participation and access

Let students work solo or in pairs. In pairs, switch driver/navigator at minute 13. Keep the sketch and three build chunks visible throughout. Read steps aloud once, then leave them in writing. Permit a preplaced layout or partially connected blocks without changing the success test. Use visual captions with audio tasks; never require personal photos.

Use a 30-second peer test at the end: the tester tries an input the builder did not use and says what happened. The builder then names one adjustment. This is a light version of investigate → design → prototype → test → revise. At the start of the next class, display one anonymous, easily fixed bug as a “mystery”: students predict the cause before the fix is shown.

Assessment without surprise syntax

For minor checks, submit a working app plus the two test cases stated in the cycle. Score the first fully working submission 100; the second 95; the third 90; then subtract 5 per further attempt. An attempt counts when the student says the app is ready for evaluation; ordinary Run clicks and peer debugging do not consume attempts. Give one precise next step after each unsuccessful submission. This preserves iteration and the grading rule you specified.

Major 1 · Study Sprint Plan

Five criteria, 20 points each. A functional text input supplies the task; a dropdown supplies a duration; a checkbox changes the quiet-space wording; a button triggers the plan; a label displays the combined result. Test two tasks, two durations and both checkbox states. The teacher supplies variable and conditional blocks.

Major 2 · Focus Break Coach

Five criteria, 20 points each. A grouped radio choice changes activity; a slider changes minutes; a text area contributes a note; a button triggers a suggestion; a label displays the combined result. Test both radio states, two slider values and two notes. The teacher supplies conditionals and string joining.

For each major criterion, award 20 if its element is present, named meaningfully and changes or displays the correct value in the complete app; otherwise award 0 for that criterion. A layout-only element does not earn functional credit. Students may repair and resubmit; keep the five functional criteria as the major score. Tell students the five checks before they build.

Vocabulary in student language

Introduce terms when students use them. Ask for an example from the current mini app rather than memorized definitions alone.

TermStudent-friendly meaningCurrent-unit example
InputData or an action the user sends to the app.Typing a name; clicking a button.
OutputInformation the app sends out.A changed label, picture, chart or sound.
User interfaceThe controls and displays through which a person uses an app.The whole phone screen.
ElementOne UI part in Design Mode.A button, slider, or label.
PropertyA setting of an element.Text, color, size, options, min/max.
Element IDThe unique name code uses to find an element.makeButton differs from MakeButton.
ProgramA collection of statements that runs.The app code.
Program statementOne command in a program.setText changes a label.
Sequential programmingStatements run in order.First hide one image, then show another.
Event-driven programmingStatements run when an event occurs.Click runs an onEvent handler.
CommentA note in code for people; it does not execute.// Read the selected choice.
DocumentationA written explanation of a design or code choice.A note explaining an ID or test.
DebuggingFinding and fixing a problem.Check ID, event, property, then output.
PrototypeA version built to test an idea.A one-screen mini app.
Development processInvestigate, design, build, test and revise.Sketch → build → peer test → improve.
Pair programmingTwo people share one build, alternating driver and navigator.Switch roles after the guided practice.
